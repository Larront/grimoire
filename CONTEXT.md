# Grimoire — Design Context

## Core Design Principles

- **GM clarity under pressure** — the interface must never become an obstacle. Information is one action away at all times.
- **The tool disappears, the world remains** — chrome stays invisible. Character lives in empty states, arrival screens, and named world content.
- **Restrained by default, expressive where it counts** — structural UI is purposeful. Arrival moments (splash, empty states, scene dashboard) get richer treatment.
- **Always session-ready, never session-gated** — no explicit session mode. The interface is equally usable for prep and live play without switching posture.

## Design Language

### Two Voices

The app has two typographic voices that map to a content boundary:

| Voice | Font         | Applies to                                                    |
| ----- | ------------ | ------------------------------------------------------------- |
| Tool  | Nunito       | All UI chrome: sidebar, tabs, buttons, metadata               |
| World | Metamorphous | Anything the GM authored: note titles, map names, scene names |

The boundary is **content ownership** — if the app constructed it, Nunito. If the GM named it, Metamorphous. This boundary holds even for the same piece of text in different contexts (a note title in the tab bar uses Nunito; the same title in the editor heading uses Metamorphous).

### Accent System

Five named presets drive `--primary`. All are evocative, never generic — no neutral greys, no corporate blues.

| Preset    | Dark hex  | Light hex |
| --------- | --------- | --------- |
| `crimson` | `#c4685e` | `#8a2e26` |
| `arcane`  | `#a48dd8` | `#5a3fa0` |
| `verdant` | `#7fb38a` | `#2f6b48` |
| `ice`     | `#7faec7` | `#2c6896` |
| `amber`   | `#d3a14a` | `#8a6418` |

`--primary-subtle` (16% opacity) and `--primary-muted` (40% opacity) are derived from `--primary`. There is no separate `--accent` token — `--primary` is the single accent family.

### Color Families

Five semantic families. No sixth family. No decorative color use.

- `--background`, `--background-subtle`, `--background-elevated`, `--background-border`
- `--foreground`, `--foreground-muted` (66%/62% opacity), `--foreground-faint` (42% opacity — sub-AA, decorative only)
- `--primary`, `--primary-foreground`, `--primary-subtle`, `--primary-muted`
- `--error` (`#d4645a` dark / `#a02020` light) — destructive actions, failures
- `--success` (`#6ab187` dark / `#2e6e4a` light) — system confirmations only

### Focus Ring

Tracks `--primary`. 2px solid, 2px offset. Uses `:focus-visible` only.

### Border Radius

| Context                             | Radius |
| ----------------------------------- | ------ |
| Structural (rows, inputs, buttons)  | 6px    |
| Elevated (cards, popovers, palette) | 8px    |
| Pill tags / chips                   | 100px  |

### Default Theme

Dark. Light and System are available in Settings.

## Layout

### App Shell

`[ Icon Rail ] [ Sidebar ] [ Main Content ] [ Right Rail ]`

- **Icon Rail** — always visible, 48px. Brand mark (re-expand to last section), Search, Files (expand + activate file tree), Scenes. Settings lives as a subdued footer icon, not a primary rail item.
- **Sidebar** — docked on ≥1024px (default open), overlay on ≤1023px (default closed).
- **Right Rail** — 300px. Docked on ≥1024px. Overlay on ≤1023px. Mutually exclusive with sidebar overlay (opening one closes the other). In split view, follows focus — shows metadata for the active pane's document.

### Overlay Mutual Exclusion

At ≤1023px, sidebar and right rail are both overlays. They cannot be open simultaneously — opening one closes the other.

### Settings

Opens as a dialog. Not embedded in the sidebar, not a full-screen page.

### Scene Player Panel

Invisible until at least one scene exists in the ledger. Once a scene exists, the collapsible panel persists at the bottom of the sidebar scroll area above the footer.

## Domain Terms

### Scene

A named container of audio slots used during tabletop sessions. Scenes have a visual identity (thumbnail), a favorite flag, and an ordered list of slots. They are the primary unit of audio scene-setting during live play. Referenced from a note by a ` ```scene ` fence carrying the scene's **id** (the truth) and its **name** (a legible copy the DB owns, kept fresh by rewriting notes on rename — a second *caller* of the note-rename rewrite path, never a second writer) — the one [[Note Block]] that references something with no ledger path, and therefore ADR-0016's documented exception whether written as a fence or as the legacy `<scene-block>` HTML the fence replaced. The fence makes the reference **legible, not legal**. Collapse of its mixer is view state and never reaches the file; the legacy tag has **no reader**, so one hand-pasted into an up-to-date vault is dropped rather than silently repaired.

### Scene Thumbnail

The visual identity of a scene card. Composed of two independent layers:
- **Background layer** — user-uploaded image, or derived accent color when no image is set
- **Icon layer** — a Lucide icon (default or user-overridden) that renders on top of both image and color backgrounds

The icon persists regardless of whether an image is uploaded. Uploading an image replaces the color background only — the icon layer is always present.

### Fallback Thumbnail

The thumbnail treatment when no image has been uploaded: derived accent color + icon. Both layers are independently user-overridable (stored as nullable `thumbnail_color` and `thumbnail_icon` on the scene). `NULL` means "use the derived/default."

### Scene Dashboard

The primary scene management surface, opened via "All Scenes" in the sidebar. Rendered as a tab in the active pane. Displays a grid of scene cards ordered: favorites first, then creation order. Contains a header toolbar with a "+ New Scene" button.

### Scene Editor

The individual scene configuration surface (ScenePane). Opened as a tab. Layout: hero header (thumbnail + scene name overlaid + play controls), then the slot list below. The primary place to manage slots and scene appearance.

### Slot

A single audio source within a scene. Sources are `local` (ledger-relative audio file path) or `spotify` (Spotify URI). Slots have per-slot volume, loop toggle, shuffle toggle (Spotify playlists only), and integer order. One scene has many slots; deleting a scene cascade-deletes its slots.

### Details Pane

The pane-local detail surface for a pane's active entity, rendered by the shared `DetailPanel` shell. Each pane owns its own surface, toggled independently by the user (see [ADR-0006](./docs/adr/0006-pane-local-detail-surface.md)). Presentation is width-based: **docked** (rail on the pane's right edge) when the pane is wider than the dock threshold (~820px), **floating** (anchored overlay) when narrower. Maps always float so the surface never shrinks or occludes the canvas. With no split, the single full-width pane's docked rail sits at the window edge, identical to the former app-level rail. Bodies differ per entity (`NoteDetails`, `PinDetails`, `AnnotationDetails`); the shell, section kit, controlled edit contract, and tokens are shared. **Describes a whole entity and never a part of one** — it is about the thing the pane holds, not about where the cursor sits, so a selected [[Note Block]] contributes nothing to it and it needs no knowledge of selection within a note.
_Avoid_: "right sidebar" (confusable with the left sidebar), "inspector," "properties panel," "app-level rail" (it is pane-local now), "context panel" (it does not follow the cursor).

### Command Bindings

The generated, committed TypeScript file (`src/lib/bindings.gen.ts`) that tauri-specta emits from the Rust `#[tauri::command]` definitions — one typed async function per command, plus the shared type mirrors. Never hand-edited; regenerated by running the app in debug (export happens in `run()` under `#[cfg(debug_assertions)]`). See [ADR-0009](./docs/adr/0009-tauri-specta-typed-command-bindings.md).
_Avoid_: "the API" (overloaded), "stubs," "the invoke layer" (that's the wrapper below).

### Command Wrapper

The single hand-written boundary module (`$lib/api`) that re-exports the Command Bindings with the project's error posture applied and carries the few commands specta can't type (the `create_annotation` arity carve-out). Frontend code imports commands from here, **never** from `bindings.gen.ts` directly. Two surfaces (see [ADR-0010](./docs/adr/0010-command-error-posture.md)): **`api.*`** toasts a GM-friendly message on failure then rethrows; **`api.silent.*`** logs then rethrows (no toast) — for background work with its own error UI (the [[details-source]] modules) and fire-and-forget calls. Both always log and rethrow, so no command fails without a trace or silently proceeds as if it succeeded. It is also where the **link-index freshness obligation** lives: a command that rewrites note bytes or adds/removes a note row (`LINK_WRITING_COMMANDS`) bumps `linksTick` on success, so Backlinks and Outbound reload for every open note without a call site remembering to say so.
_Avoid_: "service layer," "client" — it is a thin posture-and-carve-out adapter over generated code, not a service.

### Error Code

A stable `ERR_CODE:` prefix a Rust command puts on its error string for the small set of failures that are genuinely actionable by the GM (the catalog in `$lib/api` is the list; `ERR_NAME_TAKEN`, `ERR_EMPTY_NAME`, `ERR_BAD_NAME`, `ERR_MOVE_INTO_SELF`, `ERR_UNSUPPORTED_IMAGE`, `ERR_UNSUPPORTED_PDF`, `ERR_SPOTIFY_AUTH`, `ERR_DB_LOCKED`, `ERR_DB_CORRUPT`, and the [[Ledger Format Version]] refusals `ERR_FORMAT_AHEAD`, `ERR_FORMAT_MIGRATION_REQUIRED`, `ERR_FORMAT_STAMP_UNREADABLE`). The [[command-wrapper]] matches the prefix to friendly copy; everything else gets one generic line. A convention, not a typed enum (see ADR-0010). The raw detail is always logged, never shown to the GM.
_Avoid_: "error enum" (it is a string convention), "error type."

### Details Source

The per-entity reactive module that feeds a Details Pane body. It owns everything between the body and the backend: the fetch fan-out (tags, aliases, collisions, backlinks, outbound links, categories…), the refresh invariants ("alias save → re-check collisions", "any note save → reload backlinks via linksTick", "a `ledger:rebuilt` from the [[Ledger Watcher]] → refetch"), and **every save the panel offers**, all reported through one shared [[Save-Status Machine]] the `DetailPanel` shell renders. One per entity kind (`note-details-source.svelte.ts`, `pin-details-source.svelte.ts`, `annotation-details-source.svelte.ts`), instantiated by the pane, feeding the body through ADR-0006's controlled props. Bodies never fetch; panes never choreograph — a source subscribes to the [[Ledger Watcher]]'s events itself rather than having a pane relay them. What stays with MapPane is the pin and annotation **lists**, which the canvas draws from, along with the canvas's own writes (drag, placement, the undo-deferred pin delete); what moved to the source is the **panel's** save path, which commits each saved row back through an `applyPin` / `applyAnnotation` callback. Those are two different needs, and separating them is what lets a pin title or an annotation label report `Saved` / `Save failed · Retry` instead of failing into an unhandled rejection or a `console.error`. It also sets the error-posture rule: a write with an indicator to fail into takes the quiet [[Command Wrapper]] surface, a write without one stays loud, so no failure is reported twice or not at all.
_Avoid_: "details store" (it is instantiated per pane, not a global singleton), "controller" (MVC connotations the codebase doesn't use), "details data" (says nothing about owning invariants).

### Save-Status Machine

The one `idle → saved → error` machine (`details/save-status.svelte.ts`) every [[Details Source]] reports through, and the thing `DetailPanel` renders as a `Saved` flash or a `Save failed · Retry` button. Two contracts callers depend on: `run(attempt)` **never rejects** — save paths are reached from bare `onblur` handlers with nowhere to put a rejection, so the machine is where a failure stops — and `retry()` **replays the attempt that failed**, over the values that attempt captured, not whatever the body holds now. It clears its own flash timer and closes itself on teardown, so a source unmounted within the flash window writes no state after its owner is gone.
_Avoid_: "save state" (collides with `$state` and with the note buffer's dirty/clean state), "toast" (this is in-panel and non-dismissing — the [[Command Wrapper]] owns toasts).

### Ledger Event Contract

`lib/ledger/events.ts` — the frontend half of the [[Ledger Watcher]]'s event contract that ADR-0013 named and nothing owned. One `LedgerEvents` interface maps every emitted name to its payload and says what each means, and `onLedgerEvents({...})` subscribes to any subset, returning one teardown that is safe to call before Tauri's `listen` promises resolve, and a no-op outside Tauri. Before it, the names lived as loose strings in two components with different overlapping subsets, which is why a [[Details Source]] could not subscribe to `ledger:rebuilt` itself and needed `NotePane` to relay it.
_Avoid_: "event bus" (nothing is emitted from the frontend — this is subscribe-only, over Tauri's own transport).

### Tag

A colorless, cross-cutting semantic label applied to a note or pin. Ledger-global namespace (the same tag string means the same tag everywhere). For notes, tags live in markdown frontmatter; for pins, in SQLite. Never visually color-coded.
_Avoid_: "category" (that's a pin-specific concept), "label" (overloaded with UI labels).

### Pin Category

A per-map visual grouping for pins, defined by name + icon + color. Distinct from a Tag: a Category is a visual identity scoped to one map; a Tag is a semantic label that crosses maps and entity types.
_Avoid_: using "tag" and "category" interchangeably.

### Template

A static markdown file stored in `ledger/.grimoire/templates/`. Its filename (minus `.md`) is its display name in the template picker. When used to create a note, the file's full content — including any frontmatter (e.g. `tags: [npc]`) — is copied verbatim into the new note. No variable substitution.
_Avoid_: "note template" (redundant — templates always produce notes), "snippet" (implies fragment, not a full document structure).

### Templates Section

The collapsible section at the bottom of the Files sidebar that lists all files in `ledger/.grimoire/templates/`. Provides inline rename and delete, and a "+" header button to create new templates. Distinct from the note/map file tree — templates are not part of the ledger note hierarchy.

### Command Palette

The modal surface (`AppSearch.svelte`) hosting both ledger search and command execution. Opened by the Search rail icon or Ctrl/⌘+K. Single canonical surface — there is no separate "search sidebar" or "command-only" palette. Results are rendered in fixed grouped sections: Commands → Tags → Notes → Maps → Scenes. Empty state shows a Recent section above Commands.
_Avoid_: "search modal," "command bar," "quick open" (overloaded with VS Code semantics).

### Derived Index

The collective name for the four indexes derived from a note's content that must stay consistent with it on every note write: the tag index (`note_tags`), the Link Index (`note_links`), the alias index (`note_aliases`), and the Search Index (Tantivy). SQLite-backed derived indexes are canonical-adjacent and written transactionally; the Search Index is regenerable and non-fatal (see ADR-0004/0005). Reconciling all four against a note's content is the job of the `note_index` module's `reconcile`/`remove` operations — no command updates them piecemeal.
_Avoid_: "secondary index" (general DB term), "cache" (implies disposability; the SQLite-backed ones are authoritative for their relation).

### Search Index

The Tantivy index at `ledger/.grimoire/search-index/` powering the Command Palette. Holds one document per searchable entity (note, map, scene); tags are a faceted multi-value field on note documents. Derived from SQLite + the ledger filesystem and fully regenerable from a ledger scan. SQLite remains the canonical entity store; the Search Index is never the source of truth.
_Avoid_: "search database" (it isn't a database), "fts index" (specific to the rejected FTS5 alternative).

### Link Index

The SQLite `note_links(source_id, target_path)` table tracking every wikilink extracted from note content. `source_id` is the authoring note's SQLite id; `target_path` is the raw `[[...]]` text as written (path-keyed, not id-keyed). Rows where `target_path` matches no `notes.path` or `note_aliases.alias` represent links to Stub Notes. Populated incrementally on every `save_note`; fully regenerable from a ledger scan on `open_ledger`. See [ADR-0005](./docs/adr/0005-link-index-path-keyed.md).
_Avoid_: "backlinks table," "link database."

### Backlink

An inbound wikilink: a note that references the current note via `[[...]]` syntax. Surfaced in the Details Pane (Backlinks section) and the Graph Pane. The opposite of an Outbound Link.
_Avoid_: "incoming link," "inbound reference."

### Outbound Link

A wikilink authored in the current note body that points to another note. Displayed in the Details Pane below Backlinks. Broken outbound links (pointing to Stub Notes) are shown dimmed with a "not yet created" indicator.
_Avoid_: "forward link."

### Link Resolver

The single shared answer to *"does this wikilink target resolve?"* — the `path` match, else [[Note Alias]] lookup rule that decides whether a link is real. A **ledger-level** service, deliberately not part of the note-block pattern: two of its three current call sites (the broken-link decoration plugin, the click handler) are plain-editor code and know nothing about blocks. Exposes **two entry points over one rule**: a cached synchronous read for *drawing* a link (last known answer, defaulting to **known**, so a real link never flashes as a [[Stub Note]]), and an authoritative async check for *acting* on one (navigate-vs-create, which writes a file and so may not trust a memory). One cache for the whole app, invalidated wholesale whenever the notes store changes.
_Avoid_: "link checker" (it answers for navigation as well as styling), "link cache" (the cache is one of its two faces), "block link helper" (it is not block machinery).

### Linked Text Field

The one text surface a note block has for free-text values — a plain `<input>`/`<textarea>` that renders literal `[[...]]` as live links in display mode and offers `[[` autocomplete in edit mode, built on the [[Link Resolver]]. Exists only because fence-owned text is not ProseMirror content: **ProseMirror-owned content uses the wikilink node, fence-owned text uses this field, and there is no third mechanism.** Permanently plain text, never a nested editor. Renders by splitting its string into text and link segments that Svelte draws normally — never by building an HTML string — and emits `data-wiki-link` / `data-path` / `data-title` so the host surface's delegated handlers provide navigation and hover preview. It holds no opinion about saving: it reports that its text changed and the block decides when that becomes a note edit.
_Avoid_: "wikilink input," "rich text field" (it is deliberately not rich), "block editor" (it edits a string, not a document).

### Stub Note

A note that is referenced by a wikilink but does not yet exist on disk. Stub notes appear in the Graph Pane as dimmer, smaller nodes. Clicking a stub node in the graph creates the note with the link text as its title and opens it in the active pane.
_Avoid_: "ghost note," "missing note," "placeholder note."

### Orphan Note

A note with no inbound or outbound wikilinks. Appears in the Graph Pane as a disconnected node. Not hidden by default.
_Avoid_: "unlinked note," "isolated note."

### Note Alias

An alternative name for a note, usable in wikilink resolution. Stored in frontmatter (`aliases: [...]`), indexed in the SQLite `note_aliases(note_id, alias TEXT)` table. When typing `[[alias text]]`, the wikilink suggestion dropdown shows the note whose alias matches. Wikilink-resolution-only — aliases do not affect how the note title displays anywhere in the app.
_Avoid_: "note nickname," "alternate title."

### Graph Pane

The ledger-wide force-directed graph. Opened as a tab (one max — opening when a graph tab already exists navigates to it). Entry points: Graph rail icon (opens the pane directly, no sidebar step) or the *Open graph view* command. Nodes represent notes (including Stub Notes) and maps; edges represent wikilinks (note→note) and pin references (map→note via `pins.note_id`). Rendered with Cytoscape.js.
_Avoid_: "knowledge graph" (too broad), "graph view tab."

### Timeline

An inline note widget that displays an ordered sequence of Timeline Events. Authored in the note body via the `/timeline` slash command and rendered as a custom TipTap block. Its data lives in the note's own markdown (it is note content, not a referenced entity), serialized as a fenced ` ```timeline ` code block so the events stay legible in any markdown tool. A note may contain more than one Timeline. **Grammar (as migrated): each event begins with a `#` heading carrying its title**, followed by an optional `Date:` line, and then free description prose in which blank lines are legal. The old grammar (`Title:` as a labelled line, blank lines as record boundaries) silently split a hand-authored two-paragraph description into two events on the next autosave; the `#` form matches [[Infobox]] and [[Statblock]], where `#` also names the thing. One documented collision remains, handled rather than solved: a description line that is itself a column-0 `#` heading would read back as the start of a new event, so the serializer writes it with a single leading space — the one place the format edits what the GM typed, which is why the [[Format Migration]] raises a warning wherever it has to do it.
_Avoid_: "timeline entity" (it is not SQLite-backed like a Scene), "history" (overloaded with undo).

### Timeline Event

A single entry in a Timeline. Has a **date label** (free-text — "3rd of Frostfall", never a parsed calendar date), a **title** (serialized as the event's `#` heading, which is also what marks where one event ends and the next begins), and an optional **description** (free prose, blank lines and all). Title and description are plain strings that may contain literal `[[wikilinks]]`, which render as clickable links and feed the Link Index, Backlinks, and Graph exactly like prose wikilinks. Events have no chronological sorting — their order is the order the GM arranges them.
_Avoid_: "milestone," "entry" (too generic).

### Note Block

A Grimoire-authored TipTap node placed inside a note — Image, [[Scene]], [[Timeline]], [[Infobox]], [[Statblock]], [[Callout]]. Stock markdown nodes (tables, task lists, plain blockquotes) are editor features the pattern says nothing about, recorded as dispositions so nobody builds a Grimoire block for work TipTap already does. Governed by [ADR-0016](./docs/adr/0016-note-block-pattern.md): content lives in the note as plain markdown unless it is a reference to something with a ledger path; a fenced block's body is line-oriented plain text with literal wikilinks and tested round-trip fidelity; a block *declares* itself to the markdown reader rather than being found by a raw-text scan. Comes in exactly two shapes — **sealed** (no ProseMirror children) and **container** (children ProseMirror owns) — and shares exactly two pieces of machinery, the node-view connector and the [[Row List]]. Everything else is per block by design: the format inside its fence, how it looks, what it means, and anything outside the note.
_Avoid_: "custom node" (true of the wikilink node and the slash menu too, which are not Note Blocks), "widget," "embed" (a specific reference shape, not the category), "component" (collides with Svelte components, of which a block has one).

### Row List

The shared machinery for an ordered list of rows inside a [[Note Block]]: order, and the hover-revealed move-up / move-down / delete / insert-between controls. **Content-agnostic** — it knows nothing about what a row holds, and each block draws its own row. Used by [[Timeline Event]]s, [[Infobox Row]]s, and both a [[Statblock]]'s header rows and its entries. Distinct from the labelled-row *format* (`Label: value`, shared by Infobox and a Statblock header and parsed byte-identically): a Timeline uses the Row List and not the format, which is why the two are named apart.
_Avoid_: "table" (no columns, no header row, not a stock table), "repeater," "field list" (a Statblock has fields, an Infobox has rows — and the Row List holds both plus prose entries).

### Infobox

An inline note block holding a compact panel of labelled facts about its subject — authored via the `/infobox` slash command and rendered as an **atom** TipTap node. Carries an optional **title**, an optional **thumbnail image**, and an ordered list of [[Infobox Row]]s; nothing else. Its data *is* note content (like [[Timeline]], unlike [[Scene]]), serialized as a fenced ` ```infobox ` block whose title is a `#` line and whose image is real `![alt](path)` syntax. A note may contain more than one. **Inert once authored** — no part of an Infobox is mutated during play, which is the line that separates it from a Statblock: an Infobox is *read*, a Statblock is *played*. (A Statblock is equally pure note content with no identity outside its note — see the Statblock rows below — so mutation-during-play and sectioned prose entries are the whole of the difference, and the header grammar is byte-identical between the two.) Presentation floats beside the prose where the pane is wide enough and falls back to a full-width stacked panel when narrow, but the float is CSS only and never stored in the note; "wide enough" is measured on the block's **own column** rather than the window, and means enough room for readable prose beside the panel (~640px). Stacked, the thumbnail holds its floated size rather than growing with the panel. Independent of frontmatter by doctrine: **frontmatter holds what the tool consumes** ([[Tag]]s, [[Note Alias]]es), **an Infobox holds what the reader sees**.
_Avoid_: "properties panel" / "property sheet" (that is the frontmatter-passthrough surface the Details Pane deliberately rejected), "metadata block" (frontmatter is the metadata store), "sidebar" (it is note content, not chrome), "statblock" (a different block — see above).

### Infobox Row

A single `label: value` pair inside an [[Infobox]]. Labels are freeform per-instance — there is no reusable field set (that is the Statblock question). Values are plain strings that may contain literal `[[wikilinks]]`, which render clickable and feed the [[Link Index]], [[Backlink]]s, and the [[Graph Pane]] exactly like prose wikilinks. Rows are inert: never decremented, ticked, or otherwise mutated during play. The ordered row list is a **shared primitive** — a Statblock's header is the same structure — owned by the Note Block pattern rather than by either block.
_Avoid_: "field" (implies a defined schema: a Statblock has fields, an Infobox has rows), "property," "attribute" (collides with TipTap node attrs).

### Statblock

An inline note block holding a creature's stats and abilities, authored via the `/statblock` slash command and serialized as a fenced ` ```statblock ` block of line-oriented plain text. Pure note content with no identity outside its note (see the Statblock rows below). Its body is an optional `#` name, a **header** of `Label: value` rows parsed identically to [[Infobox Row]]s, then zero or more `## Section`s of **named prose entries**; a paragraph with no colon on its first line is unnamed prose. **Position, not syntax, distinguishes a row from an entry** — the same line is a row above the first `##` and an entry below it. A fence with no sections is header-only, which is exactly an [[Infobox]] with pools. Grimoire models three structural things only — rows, sections, entries — and never an entry's *kind*: `## Actions` and `Relentless (3) - Passive:` are both just characters the GM typed. The line against Infobox is *an Infobox is read, a Statblock is played*, and "played" means it carries [[Statblock Pool]]s. **Two normalisations are accepted and documented** rather than met later: a blank line is decoration everywhere *except* between two entries, where it is the record boundary — so a hand-authored blank line between header rows, under a section heading, or trailing at the end of the fence is dropped on the next autosave, and an entry can never contain one. Two lines the format would otherwise re-read as structure are handled without touching the GM's characters: an unlabelled row or unnamed paragraph that opens `#` or `## ` is written with a shield (a bare `#` line, or a leading `: `), exactly as an [[Infobox]] shields a title-shaped row.
_Avoid_: "monster" / "creature" (a statblock may describe an NPC, a vehicle, a hazard), "stat block" (one word in this codebase), "statblock entity" (there is no entity), "schema" / "template" (labels are freeform per instance; shape reuse is a preset, stamped once).

### Statblock Pool

A [[Statblock]] value the GM mutates during play, recognised **by its syntax alone** — a fence carries no schema, so the affordance has to be legible in the characters. Two shapes: `N/M` (a pool: `HP: 120/135`) and a run of `[ ]`/`[x]` tokens with optional trailing labels (a mark track: `HP: [x][x][ ][ ]`, `Conditions: [x] Prone [ ] Charmed`). Everything else, **including bare integers**, is inert. Clicking a pool opens an inline input that takes arithmetic — signed is a delta (`-20`), unsigned is absolute (`20`), empty is a no-op — with no clamping and no dice. **Playability is authored, not inferred:** a GM makes any value playable by writing it in one of these shapes, which is how ad-hoc markers a rules-feature invents get tracked without Grimoire knowing what they mean. Grimoire attaches no direction or meaning to a pool, so there is no "reset to full."
_Avoid_: "resource" / "counter" (implies Grimoire knows what it tracks), "HP field" (HP is one instance), "tracker" (suggests a separate tracking layer; there is none — the pool *is* the stored value).

### Statblock Preset

A named lump of `statblock` fence text that `/statblock` stamps into a note. **Not a schema and not a [[Template]]:** it holds whatever a fence can hold — headings, named entries, values, [[Statblock Pool]]s — and copy-on-insert leaves no id behind, so a preset is text to paste and nothing more. Stored **app-wide**, as a single JSON file in the app data directory, shared by every vault; note [[Template]]s remain per-ledger markdown. Which preset `/statblock` stamps is a **per-vault default** (`.grimoire/prefs.json`), and a GM reaches another by argument: `/statblock goblin` uses the `Goblin` preset if a case-insensitive whole-argument match exists, and in either case titles the block `# Goblin` — **the argument is always the title**. An unset or unresolvable default yields a blank statblock silently; **Blank is not a preset, it is the absence of one**. The two shipped presets are read-only code constants, so the JSON holds only what the GM made. A GM authors one by saving an existing block's shape — captured verbatim, values included — and edits one by stamping it, changing it, and saving over the name; there is no preset editor.
_Avoid_: "statblock template" (a [[Template]] is a whole note at a different scope and store), "schema" / "statblock type" (labels are freeform per instance and nothing reads a preset after insertion), "bestiary" (a preset is a shape, not a creature library — see the Statblock rows), calling the shipped presets "defaults" (they are constants; the *default* is the per-vault pointer).

### Condition

**Not a Grimoire concept.** A condition is a label the GM typed inside a [[Statblock Pool]] mark track — `Conditions: [x] Prone [ ] Charmed` — and nothing else. There is no condition vocabulary (shipped, per-system, or per-ledger), no condition storage, no condition type, and no icon, tooltip, or rules-text lookup. Grimoire never learns the word: it sees a mark track, the same one it would see in `Spell Slots: [x][ ][ ]`, and the affordance that ticks a box cannot tell that this box means *poisoned*. Conditions carry **no data** — a numeric level is a pool the GM writes (`Exhaustion: 3/6`), and a duration is either characters in the label (`[x] Poisoned (2 rds)`, noted but not tracked) or its own pool (`Poison: 2/2`, clicked down). Durations are deliberately not modelled because a countdown needs rounds, and rounds are initiative, which is out of scope. Not a [[Tag]]: a Tag is the archetype of *what the tool consumes* — ledger-global namespace, `note_tags` index, [[Search Index]] facet, [[Graph Pane]] colour, an explicit "Create new tag" step guarding against typos that would silently fail to join a queried set — while a condition is the archetype of *what the reader sees*, scoped to one fence, indexed by nothing, and typo-proof only in the sense that a misspelling is visible immediately to the person who typed it and breaks nothing.
_Avoid_: "condition field" / "status effect" / "status" (all imply a tracked thing with a type), "condition vocabulary" (there is none), calling a condition a [[Tag]] or reusing the tag chip editor for one.

### Encounter

**A note, not a block.** A fight the GM has prepared, written as an ordinary note from the built-in `Encounter.md` [[Template]] — `## Description` / `## Monsters` / `## Loot` / `## Notes` — where `## Monsters` holds one [[Statblock]] fence per creature. There is no Encounter node, no roster attr, and no surface anywhere in Grimoire that knows a fight is a fight: grouping is the `## Monsters` heading, ordering is where the fences sit in the note, and naming an instance is `# Kobold A` inside its fence. A GM who wants a fight visually grouped puts the fences inside a [[Callout]] (`> [!encounter] The Ambush`), which is theirs to author. Grimoire ships `encounter` as a styled type in the Callout picker — an icon and a colour, nothing more — which is presentation naming a domain concept, not the model knowing one: there is no roster, no Encounter node, and no query that can ask which fights a note contains.
_Avoid_: "Encounter block" (there isn't one), "roster" / "roster entry" (implies a modelled collection), "combat tracker" (initiative is out of scope), "encounter entity" (an encounter is a file like any other note).

### Callout

An inline note block holding a boxed aside — a warning, a bit of read-aloud text, a grouped fight. **Not a new node: it is the ordinary blockquote carrying two optional attrs**, a **type** and a **title**, exactly as in Obsidian, where a callout *is* a blockquote whose first line begins `[!type]`. A quote with neither attr is an ordinary quote. Serialized natively as `> [!type] Title`, so it degrades to a real callout in Obsidian and an indented quote anywhere else. The **type vocabulary is open** — a type is a word the GM typed, styled if Grimoire recognises it and neutrally if not, with no autocomplete and no validation; ten types ship in the `/callout` picker (`note`, `info`, `tip`, `warning`, `danger`, `question`, `example`, `quote`, `read-aloud`, `encounter`), matched case-insensitively with the GM's casing preserved in the file. The **title is optional** and is a [[Linked Text Field]] (block-owned text, per the [[Link Resolver]] seam), defaulting to the type word in title case. Its **body is ProseMirror-owned and unrestricted** — any block-level content, nesting included, fences included, which is what makes it the [[Encounter]] grouping vehicle — and may be **empty**, so a title-only Callout round-trips unchanged. Obsidian's `-` fold marker is honoured as an authored *starting* state and never written by Grimoire; per-block collapse remains view state that never touches the file. The **one block whose children Grimoire does not own**, and therefore the Note Block pattern's container exemplar.
_Avoid_: "admonition" (the Sphinx/MkDocs term; the ledger's word is callout, matching Obsidian), "alert" (implies severity, and most Callouts have none), "aside" / "sidebar" (a Callout is in the flow, not beside it), "Encounter block" (`> [!encounter]` is a *type name*, not a structure — see [[Encounter]]), "callout entity" (there is none; it is note content).

### Splash

The full-window arrival screen shown whenever no ledger is open (`src/routes/+page.svelte`). Three states: **first-time** (no recent ledgers — hosts the onboarding entry), **returning** (Recent Ledgers list), and **creating** (new-ledger form). Distinct from the empty-ledger home (*"Every world begins with its first note"*), which shows when a ledger is open but holds no notes.
_Avoid_: "welcome screen," "start page," "home" (the empty-ledger home is a separate surface).

### Sample Ledger

A bundled, pre-populated example ledger the app copies to disk so a first-time GM can explore a living world — interlinked notes, a map, a timeline, a few scenes — before building their own. Surfaced via the *Explore an example world* action on the first-time Splash. Tool-voice noun; user-facing copy always says "world," never "sample ledger."
_Avoid_: "demo ledger," "template ledger" (a Template produces a single note, not a ledger), "tutorial" (it teaches by exploration, not a guided tour).

### PDF

A document file the GM keeps in the ledger, surfaced in the Files tree and opened read-only in a `PdfPane` tab. Path-addressed, not a SQLite entity (see [ADR-0011](./docs/adr/0011-pdfs-path-addressed-not-entities.md)): the tab carries the ledger-relative path the way a Template tab carries `templatePath`, never an integer id. Rendered with PDF.js ([ADR-0012](./docs/adr/0012-pdfjs-over-native-webview-viewer.md)). PDFs enter the ledger by filesystem drop-in or by folder-targeted drag-and-drop onto the Files tree (bytes copied in). The PDF feature includes [[Scene-link]] annotations, built last in the same effort.
_Avoid_: "Document" (premature generalization — there is no epub/docx roadmap), "attachment," "handout" (a use-case, not the entity).

### Tree Move

Dragging a row in the Files tree onto a folder to **re-parent** it — the GM reorganising their ledger without leaving the app ([#163](https://github.com/Larront/grimoire/issues/163)). Reorganising means changing *where* something lives and never its order: the tree is built by walking disk and sorted alphabetically (folders, then files), so there is no order to persist and **disk stays the whole story** — no `sort_order` column, no second source of truth to drift. All four row kinds drag, and each needs its own verb because each is addressed differently: a note by its row (`rename_note` with a new `path` *and* `parent_path`), a folder by a prefix sweep over everything beneath it (`move_folder`), a map by its image file, a [[PDF]] by its path. Each move verb is the **mirror of its rename verb** — a rename changes the leaf and keeps the parent, a move changes the parent and keeps the leaf — so neither can do the other's job by accident, which is exactly the confusion that once sent every renamed subfolder to the ledger root ([#162](https://github.com/Larront/grimoire/issues/162)). Both halves meet in one shared `relocate_folder_inner`, so the re-keying story (descendant paths, `parent_path`, map images, Scene-links, note_tags, Tantivy) is written once.

A drop target is a folder's **whole region** — its row plus everything nested under it — so aiming at a file inside a folder means that folder, as it does in any file manager; the innermost region claims the drop, and only the *row* lights up (a ring around a folder holding fifty notes says nothing about where the thing is going). Wikilinks are rewritten **silently** on a move, unlike the rename dialog's ask: a move leaves the note's name alone, so its bare-stem links still resolve, and nobody moves a note *in order to* break the links pointing at it. Two refusals, treated differently on purpose: a folder dropped into itself or its own descendant is a mistake worth a word, while a drop onto the folder something already sits in asks for nothing and gets silence. The tree plans a drop before accepting it, so an illegal drop never looks droppable — but the backend refuses independently, because a ledger is edited by other tools too.
_Avoid_: "reorder" / "sort" (there is no manual ordering, and offering one would make disk stop being the truth), "cut and paste" (a different, clipboard-shaped feature), "drag to import" (that is the external-file path — [[PDF]] bytes copied *in* from the OS, which shares the drop zones but not the verb).

### Scene-link

A Scene attached to a range of selected text inside a [[PDF]] — the one form of PDF annotation in scope. The GM selects text and links a Scene; the text gains a Scene-accent-tinted underline (with a trailing scene icon, and an active state while its Scene plays). Hovering the underlined span reveals an inline bubble toolbar (▶ Play/Stop · master volume · Scene name → opens the Scene editor, with a change-dropdown whose footer offers _＋ New scene_ · Remove). Anchored to a character range on a page (`pdf_scene_links(id, pdf_path, page, start_offset, end_offset, quote, scene_id, created_at)`), stored canonically in SQLite, keyed by the PDF path (the one piece of non-regenerable PDF state). `ON DELETE CASCADE` on `scene_id` removes the link when its Scene is deleted. This is the only inbound dependency a PDF places on a Scene.
_Avoid_: "highlight" (the visual treatment, not the entity; and generic highlighting is explicitly out of scope), "PDF annotation" used loosely (a Scene-link is the *only* annotation kind), "bookmark."

### Ledger Watcher

The backend `notify`-based file watcher rooted at the open ledger that keeps the app live-synced with external `.md` changes (edits, creates, deletes, moves) made by other tools — Obsidian, an editor, `git`, cloud sync. Lives entirely in `src-tauri`, drives the [[Derived Index]] `reconcile`/`remove` verbs and `rebuild_all_from_ledger` directly, and emits Tauri events (`note:content-changed`, `note:removed`, `note:moved`, `note:external-move-links-stale`, `ledger:tree-changed`, `ledger:rebuilt`) to the frontend. Starts on `open_ledger`, tears down on ledger switch / window close. Excludes `<ledger>/.grimoire/` so it never sees the app's own DB/index/media writes. See [ADR-0013](./docs/adr/0013-external-file-watching-live-sync.md).
_Avoid_: "file listener" (overloaded with DOM/event listeners), "sync engine" (implies remote/cloud replication — this is local-disk only), "hot reload" (a dev-tooling term).

### Write Chokepoint

The single `write_note_file(path, bytes)` helper all note-file writes route through (`write_note_content`, `create_note`, template creation, tag rewrite, the `rename_note` backlink rewrites, etc.), replacing ~8 independent `std::fs` calls. On each write it records a content hash of the bytes written into a bounded per-path registry on `AppLedger`, so the [[Ledger Watcher]] can tell the app's own writes from genuine external edits (**content-hash echo suppression**): a watch event whose on-disk hash matches the registry is the app's echo and is dropped; a differing hash is external. Race-free and set-valued, so it covers `rename_note` touching many files at once.
_Avoid_: "mute set" / "ignore window" (the rejected time-based scheme this replaced), "save hook."

### Write-and-Reconcile Envelope

The single recipe for persisting a note change — write the bytes through the [[Write Chokepoint]], then reconcile the [[Derived Index]] against the new content — owned by the `note_mutation` module so it is written once instead of hand-copied across `notes.rs`, `links.rs`, and `tags.rs`. Three verbs: **`commit`** (the `write_note_file` + `reconcile` envelope; takes no `prev_path` because only a rename changes a path), used by content save, tag write, and alias write — content and tag save go via the `commit_or_write` variant, which still writes through the chokepoint when the path has no `notes` row to reconcile; **`create`** (the same envelope for a brand-new note, named for its call site), used by blank and template creation; **`commit_many`** (write each file through the chokepoint, then one batched `reconcile_many`), used by the ledger-wide tag rewrite so bulk retags are echo-suppressed like every other write; and **`rename`** — the one rename implementation shared by the in-app `rename_note` command and the [[Ledger Watcher]]'s external move, so the two can never diverge. `rename` always runs **phase A** (re-key the moved note's own row to the new `path`/`title`/`parent_path` and reconcile it with `prev_path = old_path`, the single place the re-key rule is applied); it runs **phase B** (rewrite `[[old path]]` wikilinks in every other note via `commit_many` and count them) only when `rewrite_backlinks` is true, and otherwise returns the affected source paths as a deferred plan for a caller to offer later. In-app rename passes the frontend's yes/no-links choice as the boolean (replacing the former `update_note`/`rename_note` split); external moves pass `false` (phase A only), then surface the deferred plan through the [[External-Move Backlink Prompt]]. The module depends on `note_write` and `note_index` (and `links` for the wikilink rewrite) and never writes note bytes outside the chokepoint; disk I/O (`fs::rename`, name-collision checks) and the canonical `notes` row insert stay in the command. `delete` (a removal, not a write) lives outside it.
_Avoid_: "save path" (overloaded with filesystem paths), "write pipeline" (implies async/streaming), teaching `note_index` to write bytes (it only makes indexes agree with content it is handed).

### Ledger Format Version

The stamp recording which on-disk format a ledger's **notes** are written in, and the consent gate in front of changing it. The principle, settled while specing the note-block migration: **Grimoire's own store migrates silently; the GM's documents are never rewritten without being asked.** The database side already migrates on every open with no prompt (23 embedded migrations, `db/mod.rs:104`, one of them a pure data repair) and that stays — a private store owes no consent. A note-format change is different in kind: the notes *are* the ledger, and a GM hand-edits them in other tools. So an out-of-date ledger prompts on open with what will change and migrates in **one knowing pass over the whole vault**, never note-by-note as each is opened. Two hard rules it carries: the affected notes are **backed up before anything is rewritten** (the same reasoning as the DB snapshot at `db/mod.rs:121`, but stronger — a database can be rebuilt from the notes and the notes have nothing to be rebuilt from), and the migration **reports what it changed**, not merely that it ran. Once the mechanism exists it is the *sole* guard against old-format content: no compatibility shims live underneath it. Settled by [#166](https://github.com/Larront/grimoire/issues/166) and [ADR-0017](./docs/adr/0017-consented-vault-migration.md): **one integer for the whole vault** in its own file, `.grimoire/format-version`, independent of the SQLite migration count — the two migrate on opposite terms (silent-and-mandatory vs consented-and-declinable), so a shared number could not tell either side whether its own work was done. **Absence means version 0**, and Grimoire makes no attempt to tell a pre-versioning vault from a brand-new one: the distinction dissolves, because a new vault has no notes and a foreign Obsidian folder has no old blocks, so both find no work and are stamped in silence. The stamp is **not a to-do list but a statement of what format the files are in**, so the comparison has three outcomes and two are refusals — a vault *ahead* of the app does not open either (see the decision rows below). Writing the stamp is itself exempt from the consent rule: it lands in `.grimoire/`, which is Grimoire's own bookkeeping, not a document. **[[Template]]s migrate with the notes** — they are `.md` files under `.grimoire/templates/`, invisible to the note walk, and an un-migrated template would quietly produce broken notes forever.
_Avoid_: "schema version" (that is the SQLite side, which is separate and silent), "vault version" used loosely (it stamps note format, not the app or the DB), "auto-migrate" (the consent is the point), "compatibility mode" (there is none — a ledger is migrated or it is not opened), "downgrade" (declined: the old app would have to ship an understanding of a format that did not exist yet).

### Format Migration

One registered unit of note-format change: the **version it takes the vault to**, one **GM-facing sentence**, and one **function** that, given a file's text, returns either nothing (untouched) or the rewritten text plus any warnings. Registered as an entry in a const array in one module — no framework, no authoring API — with the app's target version **derived from the highest entry** rather than declared beside it, so shipping a migration that never runs is not a thing you can forget your way into. The single function is the load-bearing part: **the scan is the migration with the write left off**, run without writing to build the prompt and with writing to migrate, so the prompt cannot lie about what will be touched. Catching a vault up several versions is a **fold, not repeated passes** — each pending migration's function is threaded over the same text in version order, so a note three versions behind is read once and written once. The context handed to it is honestly minimal — the file's text, plus whatever a shipped migration cannot read out of it and nothing speculative. As shipped that is **scene names**: [[Timeline]]'s transform (format 1) is a function of the text alone, and [[Scene]]'s (format 2) writes a scene's name into the note beside its id, which was the predicted trigger for earning the database connection and the only thing it earned. The sentence is what makes the consent prompt **composed rather than written** — the dialog is assembled from the sentences of whichever migrations are pending, so nobody edits the dialog again and a vault at any distance behind renders correctly. A migration finding no work contributes no sentence; when none of them find work, there is no prompt at all. See [ADR-0017](./docs/adr/0017-consented-vault-migration.md).
_Avoid_: "migration framework" (it is an array and a function pointer), "dry run" as a separate mode (the scan is the same code; the prompt is its output), "up/down migration" (there is no down), calling the DB's Diesel migrations by this name (separate, silent, and counted elsewhere).

### Conflict Banner

The non-destructive in-pane bar shown when an open note's file changes on disk externally *while the editor buffer has unsaved edits*. Offers *Reload from disk* (take the external version) / *Keep my version* (keep the buffer, overwrite on next save) — neither side is discarded without consent. A **clean** buffer skips the banner and reloads silently. A separate variant covers deleted-while-open (*Save to recreate* / *Close*, buffer kept as unsaved). See [ADR-0013](./docs/adr/0013-external-file-watching-live-sync.md).
_Avoid_: "merge conflict" (there is no three-way merge — it's a choose-one prompt), "sync error," "unsaved-changes dialog" (it's an in-pane banner, not a modal, and it's about external divergence, not plain unsaved state).

### External-Move Backlink Prompt

The offer to heal inbound wikilinks after a note is renamed/moved *outside* Grimoire. The [[Ledger Watcher]]'s targeted move path re-keys the moved note (phase A) but leaves other notes' `[[old path]]` links as the external tool wrote them; when any remain it emits `note:external-move-links-stale { from, to, count }` (alongside `note:moved`), and the frontend shows a **persistent** `svelte-sonner` toast (`duration: Infinity`) — *"'Old Name' moved externally. Update N backlinks?"* with *Update* / *Leave as-is*. *Update* calls the `apply_backlink_rewrite` command, which performs phase B via [[Write-and-Reconcile Envelope]] `commit_many` and **recomputes** the affected set at apply time (the toast count is display-only, so a stale count can never edit the wrong notes); *Leave as-is* dismisses with no backend call. The **bulk** move path (a batch over the full-rebuild threshold) emits no prompt — the external tool owns that reorg — leaving broken backlinks visible as dimmed/Stub links, healable later by a follow-up *Repair backlinks* tool. This is the one sanctioned permanent toast: a [[Conflict Banner]]-class response to an unresolved external change, non-destructive to ignore. See [ADR-0014](./docs/adr/0014-external-move-backlink-prompt-persistent-toast.md).
_Avoid_: "broken-link fixer" (it heals a *rename*, not arbitrary broken links), "auto-update backlinks" (it never rewrites without consent), reusing "[[Conflict Banner]]" for it (that is the in-pane, open-note surface; this is a toast for a note that isn't open).

| Declining the migration | **The vault does not open** — back to the welcome screen.
